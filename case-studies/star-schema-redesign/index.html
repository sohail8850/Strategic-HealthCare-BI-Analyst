Star Schema Redesign

Headline Finding

Two flat, denormalized extracts were rebuilt into governed star schemas — explicit grain, conformed dimensions, selectively-applied history tracking, and one bridge table resolving a many-to-many relationship neither flat table could represent cleanly.

The Problem

Two working datasets — a retail order extract and a healthcare patient-encounters extract — were both flat and denormalized. Every report built on top of them had to re-derive its own business logic from scratch, the grain of each table was implicit rather than stated anywhere, and slowly-changing attributes — a patient's assigned provider, a customer's region — were being overwritten in place instead of tracked over time.

The Approach

Both datasets were rebuilt as governed star schemas, with an explicit grain statement written for every fact table and a set of dimensions conformed once rather than redefined per report. Slowly Changing Dimension Type 2 was applied only to the handful of attributes where tracking history genuinely mattered, not as a blanket default across every dimension. Where a fact table needed to relate to a dimension in a true many-to-many way — a single patient encounter carrying multiple diagnosis codes — a bridge table was introduced specifically to resolve it, since a simple foreign key couldn't represent that relationship cleanly. Every one of these modeling decisions was documented alongside the schema itself, not left implicit.

The Outcome

The result is two complete, query-ready star schemas — retail and healthcare — each with explicit grain, conformed dimensions, selectively-applied SCD2, and one bridge table handling the many-to-many case. The healthcare model in particular now gives the rest of this portfolio's patient-level projects a schema pattern to build on, rather than starting from a flat extract each time.
